# Plans follow Stripe; Plan Quotas live in our database

A Candidate's Plan is whatever their Stripe subscription says. We never set it ourselves: Stripe Checkout starts a subscription, the Stripe customer portal changes or cancels it, and our webhook (`customer.subscription.created/updated/deleted`) copies the subscription's price and status onto the Candidate. A subscription that is `active`, `trialing` or `past_due` (Stripe is retrying a payment) keeps its paid Plan; any other status, or deletion, drops the Candidate to Free. Events older than the last one applied are ignored, because Stripe does not guarantee delivery order. We rejected granting the Plan on the checkout redirect: it can be replayed or skipped, while the webhook is signed and retried.

Plan Quotas are not Stripe product metadata or code constants: they live in a `plan_quota` table that Administrators edit in the Back Office, and a change applies at once to every Candidate on the Plan. The migration only seeds the starting quotas when a Plan has none, so edits survive deployments. Monthly quotas are counted per calendar month in Europe/Paris (per week since ADR-0031), with a conditional upsert so concurrent requests can never exceed a limit. Each feature asks the billing module before doing the work (`use` / `allowsAnother`) and shows an Upgrade Prompt on refusal; quotas are never enforced in the browser.

Billing hangs off the Candidate (`candidate_plan`, `quota_usage` reference `candidate`), so an Organisation paying for its beneficiaries (ADR-0004) can be added as another payer without moving Candidate data.

Administrators are Jobbbox team members listed by email in `ADMIN_EMAILS`, signed in through the same passwordless accounts (ADR-0011) with a verified email. We rejected a role column or Better Auth's admin plugin for now: the team is a handful of people, the list is changed by a deployment, and nobody can grant themselves access from the app. Revisit when Human Coaches need their own accounts in the Back Office.

Addendum (#104): to offer invoices to a Candidate who paid and then cancelled to Free, the webhook sets a sticky `candidate_plan.charged` flag when a subscription reports `active`, `past_due`, `unpaid` or `paused` (states Stripe only reaches after a first payment), even for an out-of-order event. `billing.hasInvoices` reads it. We rejected asking Stripe for invoices on each page load: the flag keeps Stripe the source of truth with no extra network call. The backfill also counts `canceled`, safe only while our Plans have no free trial. Coaching Session payments do not set it: that checkout creates no Stripe invoices.

Addendum (#169): a Scheduled Cancellation keeps the paid Plan, so the webhook stores its date in `candidate_plan.ends_at`: Stripe's `cancel_at`, else the subscription item's `current_period_end` when `cancel_at_period_end` (the subscription-level field on endpoints pinned to an API version before 2025-03-31.basil). It goes through the same out-of-order guard, so a late event cannot bring back a stale date; it is null once the subscription ends. After `?checkout=success` the page re-reads the Plan for up to a minute while it is still Free, rather than fulfilling from the redirect: granting on redirect stays rejected.

Addendum (#193): Back Office Roles replace the single `ADMIN_EMAILS` list. Permissions are code constants declared with Better Auth's access-control plugin; who holds which role lives in our own `administrator_role` table (one row per Administrator and role, referencing `candidate`), managed by super-admins from the Back Office. `ADMIN_EMAILS` stays as the bootstrap: those addresses are permanent super-admins the UI cannot revoke, so nobody can lock the team out. Roles are read on every Back Office request (no cache). We rejected the admin plugin (it stores roles on `candidate`, mounts unused `/admin/*` routes and lets any role with `set-role` escalate itself) and runtime-editable roles (Better Auth only offers them per Organisation, out of scope per ADR-0004).

Addendum (#206): Plans are no longer code constants and env prices: they live in a `plan` table that Administrators with the Plans manager role edit in the Back Office (Offres), every change recorded in the Back Office Audit. A Plan has a permanent key (what `candidate_plan` and `plan_quota` reference), a name in each Interface Language, a rank, a status (offered or hidden), one Stripe product (`prod_…`, unique) and its Plan Features. The webhook maps `subscription.items[0].price.product` to the Plan holding that product, so every price of the product (monthly, yearly, archived older amounts) keeps its subscribers on it; other products are ignored. Checkout sells the product's default price, and the plan comparison shows it. We rejected mapping by price IDs (every price ever used must stay listed) and by lookup keys (a transferred key no longer names the old price's subscribers): research #194. The Back Office never creates Stripe products or prices; it checks a product exists, is active and has a recurring default price before tying it to a Plan. A paid Plan's product is frozen once set: replacing it would leave the subscribers still on the old product unmapped, so a cancellation would never bring them back to Free; moving subscribers is done in Stripe. The product is checked in Stripe (short timeout) before the Back Office's audit transaction opens, and concurrent Plan writes lock the `plan` rows, a unique conflict coming back as a form error. Plans are never deleted: hiding one takes it off the comparison, checkout and Upgrade Prompts, its subscribers stay and are moved in Stripe if needed. A new Plan starts hidden, ranked highest, with the Plan Quotas of the Plan ranked just below. A Plan Quota added in a later release starts, on such Plans, at the value of the Plan ranked just below (never NULL, which means unlimited). Free is built in: rank 1, always offered, no product (a CHECK constraint holds it). The rank orders the comparison and Upgrade Prompts, which name the lowest-ranked offered Plan above the Candidate's whose quotas allow the request. Plan Features are a fixed set in code, switched on per Plan; the first, the Coaching Session discount, replaces the check on the `premium` key (the discounted Coaching Session price stays in env). Migration without downtime: the table is seeded with `free`, `standard` and `premium` (ranks 1 to 3, offered, names from the i18n catalogue, the discount on `premium`), and `plan_quota`'s CHECK on the three keys becomes a foreign key to `plan`, so no `candidate_plan` row changes. At startup, a paid Plan without a product takes the product of `STRIPE_PRICE_STANDARD` / `STRIPE_PRICE_PREMIUM`, unless both prices share one product or another Plan holds it: then it is left unlinked with a warning (a product is one Plan's), and the webhook still maps those exact env price IDs to their Plans first; afterwards the database wins and those variables are optional fallbacks, to be removed in a later release.

Addendum (#207): Coupons are Stripe coupons with one promotion code each, and live only in Stripe: the Back Office's Codes promo section (Plans managers write, Support reads) creates them through the Stripe API, the one thing the Back Office creates in Stripe (never products or prices), lists them page after page with Stripe's redemption counts (one Stripe returns without its coupon shows as unreadable rather than blanking the list), and deactivates them; there is no table of ours, so a code created or deactivated in the Stripe Dashboard shows up too. A coupon's `applies_to.products` are the eligible Plans' products. A fixed amount is in euros, refused on a Plan Stripe prices in another currency, and, with a `forever` duration, refused at or above an eligible Plan's price (that Plan would be free for good). Its terms never change once created: to change them, deactivate it and create another. Stripe is called before the Back Office Audit's transaction opens, with short timeouts (a few seconds, one retry for writes); if the audit entry then cannot be written, the change is undone in Stripe (a created code deactivated, a deactivated one reactivated), so no change goes unrecorded; deactivating a code already inactive writes nothing. The "first payment only" option is Stripe's `first_time_transaction`, labelled for what it does: refused to a customer who has already paid anything, a Coaching Session included. We kept Stripe's rule rather than adding our own "first subscription" check, which Stripe could not enforce for a code typed in Checkout. Plan Checkout sets `payment_method_collection: if_required`, so a 100 % code subscribes without a card. When its free period ends, the subscription goes `past_due` with no payment method: the webhook drops the Candidate to Free at once (and shows no Payment Failed Notice) rather than keeping the Plan through Stripe's retries; should they add a card and pay, the next event brings the Plan back. Stripe's subscription settings must still cancel a subscription once retries fail (runbook: `docs/ops/billing.md`); the API does not expose that setting, so it is checked there, not at startup. A shared link `/abonnement?code=XYZ` is resolved server-side, each code's answer kept a minute and each Candidate limited to 10 lookups Stripe answers per 10 minutes (in memory, per process), so codes cannot be enumerated nor Stripe's rate limit spent. At Checkout a code that can be redeemed on the chosen Plan is passed as `discounts` (never with `allow_promotion_codes`, which Stripe refuses alongside); otherwise, whether for another Plan, expired, refused by Stripe for this customer, or not checkable, the Candidate is sent back to the subscription page with the reason and a button to go on without it, which gets `allow_promotion_codes`. The subscription page reads the subscription's discount from Stripe at render (short timeout, left out on failure) rather than keeping it from webhooks, whose `discounts` are bare IDs. Coaching Session checkout takes no code. We rejected keeping Coupons in our database (Stripe would still have to enforce redemptions, expiry and eligibility, and two records drift) and creating them only in the Stripe Dashboard (no Back Office Audit, and the Plans' products to pick by hand).
