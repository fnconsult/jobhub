# Documentation

Every delivered issue ships its public documentation in the same PR as its code. The agent drafts; the product owner validates at the Promotion (ADR-0063), where the assembled Release Note and the diff of `packages/help` since the last tag are reviewed together. The Help editor Back Office Role triages Unanswered Questions; it is not a validation step.

## What to update

Read the issue's `## Documentation` section (see `issue-tracker.md`). When it is missing, derive the impacts from the diff with the rules below. Done means every rule below has been checked against the diff, and each one that applies has its change in the PR.

- **Help Article `page`**: a PR that adds or changes a page or Section updates the `page` article of its route (`route:` in the frontmatter), FR and EN, or creates it. A new Tool or provider in the catalogue gets its line in the « Paramètres » or « Outils » article.
- **Glossary, FAQ and tutorial Help Articles**: a new term the user meets on screen gets a `glossary` article. A new task of several steps gets a `tutorial` article (ADR-0065): at least two numbered steps, which the build checks. Labels are quoted word for word from the interface. Each article declares its `audience` (`visitor`, `guest`, `candidate`, `human-coach` or `administrator`) and its `topic`: one of the Help Centre's `decouvrir`, `extension`, `utiliser`, `espace-coach` for a public article, a Back Office slug for an Administrator's, which stays out of the Help Centre, its search and the sitemap.
- **Release Note fragment**: a PR with anything a Candidate can see adds `packages/help/releases/unreleased/<pr>.md`, FR and EN (ADR-0063). A PR with nothing visible to a Candidate adds none. Its format (#562, `packages/help/src/release-note-fragments.ts`): front matter `kind` (`new`, `improved` or `fixed`), `tags` (from `RELEASE_NOTE_TAGS`, `[]` for none) and, if need be, `announce: true`; then a `## fr` section and a `## en` section, each holding the line, `- …`, for Candidates (several lines of the same kind are allowed, as many in each language). A second kind of change from the same PR goes in `<pr>-2.md`. The build of `packages/help` refuses a fragment without its English line or with a tag outside the list. Before the Promotion, `npm run release-note -w @jobhub/help` assembles the fragments into the next Version's draft, `releases/{fr,en}/X.Y.Z.md` (the Version of the root `package.json`), grouped under « Nouveau », « Amélioré », « Corrigé », and removes them; a new draft's title and introduction read « À écrire » / « To be written », which the build refuses until the agent writes them and rewrites the lines in one voice. The product owner validates it at the Promotion. `npm run release-note -w @jobhub/help -- --check` only says where it stands (the `deploy-staging` skill reports it).
- **Privacy register**: a PR that adds or changes a processing, a sub-processor, a recipient outside the EU or a tracker updates `docs/privacy/register.md` in the PR. It is internal; nothing is published.
- **Legal Texts**: the same changes may call for a new Legal Text Version. The agent never writes one in the delivery PR. It opens an issue labelled `ready-for-human`, titled « Légal : <change> », holding a draft of the changed clauses, the change that requires them, and a `/legal:compliance-check` first pass. The product owner runs the Legal Review, sets the effective date and merges (#507, ADR-0062). A version is `packages/help/legal/<texte>/<AAAA-MM-JJ>.<fr|en>.md`; a privacy policy version also declares `recipients_outside_eu: [<tool id>, …]` (`[]` for none), the Tools outside the EU it covers, and the build refuses an id not in `packages/shared/src/tools.ts` (#548): switching on any other recipient outside the EU warns in Paramètres and is written to the Back Office Audit; CI refuses a change to one already in effect (`packages/help/scripts/check-legal-immutability.ts`), and the repo's hook (`scripts/hooks/no-legal-merge.mjs`) refuses an agent's merge of a PR that touches `packages/help/legal/`.
- **Motions**: each Motion Script (`packages/help/motions/<locale>/<id>.md`, named by its Tutorial's `motion` field) declares the routes it films in its `routes:` field. A PR that changes one of those routes (`motionScriptsFilming(path)` in `@jobhub/help` lists the scripts filming a page), or a screenshot baseline (`screenshot-baselines.md`), adds a line « Motion à régénérer : <script> » to the PR body. The `motions` workflow reads those lines and renders the flagged motions together before the Promotion (`docs/ops/motions.md`).

Write the French first: it is authoritative. Keep the tone and the vouvoiement of the existing articles.
