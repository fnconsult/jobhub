# Provider Secrets are encrypted in our database, under master keys from env

Third-party keys (Mistral, Perplexity, Bedrock, France Travail, the contact-enrichment provider, Stripe, Brevo's SMTP relay) used to live only in env, injected by ECS from AWS Secrets Manager at container start. Changing one meant a deployment. Super-admins now enter them in the Back Office (the Clés section, #208), and the app keeps them in a `provider_secret` table, encrypted. A key entered there wins over env's; cleared, env's is used again; missing everywhere, its features stay off as before. Non-secret configuration (models, regions, `*_LIVE` flags, `MAIL_FROM`, Stripe Price IDs) and the bootstrap secrets (`DATABASE_URL`, `AUTH_SECRET`, `SECRETS_MASTER_KEYS`) stay in env. Research: `docs/research/issue-197.md` (branch `research/provider-secrets-encryption`); decision: #198.

How a value is kept:
- AES-256-GCM in Node (`apps/web/src/provider-secrets/cipher.ts`), a random 12-byte IV per seal, a 16-byte tag, and additional authenticated data `provider|name|row id|key version`, so a value copied onto another row, or a row whose version was edited, does not decrypt. The row id changes on every replace.
- The master keys are a keyring in env, `SECRETS_MASTER_KEYS=1:<base64>,2:<base64>`; the highest version encrypts, each row records its `key_version`. A pg-boss job (`provider-secrets.reencrypt`, nightly and at worker start) moves every row to the newest version, after which the old one can be removed (`docs/ops/provider-secrets.md`).
- The cipher sits behind a `SecretCipher` interface, so a KMS-backed one can replace it without a schema change if a buyer's security review asks for HSM-held keys or per-decrypt audit.
- Never `pgcrypto`: the value and the key would travel in SQL text, where statement logs and `pg_stat_statements` can keep them.

How the apps use it:
- One resolver, shared by the web app and the worker (`apps/web/src/provider-secrets/resolver.ts`): the database's value, else env's; a 60 s cache (on `globalThis` in the web app, whose server code Next.js bundles into several chunks); `NOTIFY provider_secrets_changed` on every change, so both apps refresh within seconds; clients that captured a key (the AI layer, Stripe billing, Enriched Contacts and its provider, the mailers, France Travail) are rebuilt when one of their keys changes, and the worker's Job discovery turns on once an AI key is entered; a call whose key is refused (HTTP 401/403, an SMTP 535, France Travail's refusal) reads the database again and is retried once if a key changed. A refresh asked while a read is in flight queues one more read, so a save is never hidden by a read that predates it; the listener keeps reconnecting with backoff.
- A value goes in, never out: the Back Office shows its source, last 4 characters (for 16 characters or more), and who changed it when. The form is write-only. The Back Office Audit records "replaced", "replaced despite a failed test" and "cleared", never a value.
- Each provider is tested on save with its cheapest authenticated call; a failure blocks the save unless the super-admin ticks "save anyway", which is recorded.
- Provider error bodies are scrubbed of keys before they are logged or stored (`scrubSecrets` in `@jobhub/shared`, used by `AiProviderError` and the Lusha adapter).
- The table names its Administrator by email only (no `candidate_id`), so it is never part of a Candidate's data export.

We rejected AWS KMS for now: it would add AWS-specific code to both apps, against the portability rule in `docs/ops/hosting.md`, and need a fake for dev, CI and e2e anyway. We accept that the master key sits in the container's env, readable by whatever can read env, as every key did until now. This amends ADR-0007's "provider keys come from env" for the keys above; data residency is unchanged (the database is in the EU).
