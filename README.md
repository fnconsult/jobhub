# Jobbbox (jobhub)

Coaching platform for job seekers aged 40+ in France. Vocabulary: [`CONTEXT.md`](CONTEXT.md). Decisions: [`docs/adr/`](docs/adr/).

## Layout

| Workspace | What it is |
| --- | --- |
| `apps/web` | Next.js web app |
| `apps/extension` | Chrome MV3 extension (WXT) |
| `apps/worker` | Background-job runner (pg-boss on Postgres) |
| `packages/shared` | Domain types, translations (`@jobhub/shared/i18n`) and design tokens (`@jobhub/shared/design`) |
| `packages/ai` | Provider-agnostic AI layer (`@jobhub/ai`, server-side only): Anthropic, Mistral, OpenAI; web search: Perplexity, Brave, Tavily, Linkup; fake provider in `@jobhub/ai/testing` |
| `packages/coach-knowledge` | Coaching Playbooks, Sources and Core Digest (`@jobhub/coach-knowledge`, server-side only): `loadCoachKnowledge({ environment })` |

## Getting started

Requires Node 22+ and Docker.

```sh
npm install
cp .env.example .env          # repo-root .env, read by `npm run dev`, `build`, `start` and `db:migrate`
docker compose up -d          # Postgres (host port 5433) + worker
npm run db:migrate            # create / upgrade the database tables
npm run dev                   # web app on http://localhost:3000
npm run dev -w @jobhub/extension   # extension, with a Chrome dev profile; its dev server is on http://localhost:3100
```

The `worker` container reads the same repo-root `.env` (AI layer keys and providers, `APP_URL`, …), so Job Searches and job discovery work locally. Its `DATABASE_URL` is overridden to `postgres:5432` inside the compose network. The `.env` is optional: without it the stack still starts, and job discovery is skipped with the reason in the worker log. After editing `.env`, run `docker compose up -d` again to recreate the worker with the new values.

## Agent Run log

Delivery workflows (e.g. `wf-dev`) can record each Agent Run in the `workflow_agent_run` table (after `npm run db:migrate`):

```sh
npm run wf:record -- --issue 31 --workflow-id wf-dev --workflow-ref .claude/workflows/wf-dev.js \
  --workflow-instance wf_c2d1ad6a-1bc --workflow-date 2026-10-06T08:00:00Z \
  --agent "wf-dev/#31/implement" --model claude-opus-5-5 --effort high \
  --time-ms 754000 --round 0 --tokens 182345
```

`--round` defaults to 0 (first pass). `--workflow-date` is an ISO 8601 date (`2026-10-06`, read as UTC midnight) or a date-time with an explicit offset (`Z` or `+02:00`). Exits with code 2 and the usage line when a flag is missing or invalid.

## Conventions

- **Translations**: every user-facing string lives in `packages/shared/src/i18n/locales/*.json`. French (`fr`) is the default and reference locale; every locale must have the same keys.
- **Accessibility (ADR-0009)**: colours and type come from `packages/shared/src/design/tokens.ts`. `auditDesignTokens` checks WCAG 2.1 AA contrast, the 16px body-text floor and every text-size setting in the test suite. Light greys are for surfaces and borders only. `auditStylesheet` applies the same floor to a stylesheet (no text under 16px, only audited text colours, no literal colours outside custom properties). The clickable layout prototype for #132 is `docs/prototypes/notion-layout.html` (one file, no dependencies, single light theme, no `<!doctype>` because the artifact host adds it); `docs/prototypes/notion-layout.test.ts` keeps its tokens equal to `renderDesignCss(designTokens)` and runs the stylesheet audit. Its layout decisions are proposals until François approves them.
- **Complex widgets (ADR-0018)**: dialogs, menus, popovers and tabs use one unstyled `@radix-ui/react-<widget>` package each (never the whole `radix-ui` bundle), styled in `apps/web/src/app/app.css` with our tokens through classes and `data-*` attributes. The Profile switcher (`components/ProfileSwitcherMenu.tsx`) is the first. No Tailwind or shadcn.
- **AI calls (ADR-0007)**: always through `@jobhub/ai` (`createAiLayerFromEnv()` → `generate` / `searchWeb` / `searchCompany`), never a provider SDK directly. The provider of each task is set by `AI_<TASK>_PROVIDER` / `AI_<TASK>_MODEL` (see `.env.example`). Tasks that carry personal data refuse non-EU endpoints at start-up and on every call; web search (`AI_WEB_SEARCH_PROVIDER`: perplexity, brave, tavily or linkup; optional domain and page-age filters) only ever receives a query built from Search Criteria, or from an employer's name for a Company Dossier (`searchCompany`; never a person's name, see the ADR-0007 amendment). With a Candidate's EU AI Consent (`eu_ai_consent`, set on `/compte`), a call that carries their identity (declare `containsIdentity: true`; undeclared phone numbers or emails are caught by a scan and logged) goes to Mistral (`AI_IDENTITY_MODEL`, needs `MISTRAL_API_KEY`), see the ADR-0007 amendment; pass `euAiConsent` to `createAiLayerFromEnv`. Every call logs its token usage per Candidate (`ai_usage` JSON lines). Tests use `createFakeProvider` from `@jobhub/ai/testing`, or `AI_FAKE=true`.
- **Coaching knowledge (ADR-0019)**: `packages/coach-knowledge` holds the 10 Coaching Playbooks (`playbooks/*.md`), `sources.md` and `core-digest.md`, in French. `loadCoachKnowledge({ environment })` gives `playbook(id)`, `playbooks()` and `coreDigest()`; in `production` only Human-validated files are served (`statut: validé (<name>, <date>)` in the frontmatter, an AI review never counts), `development` and `eval` get everything. Loading throws `CoachKnowledgeError` if a file cites a `[Sn]` missing from `sources.md` or from its own frontmatter `sources`. Today every file is marked as reviewed by an AI, so production serves nothing until a person validates them. The loader reads the `.md` files from disk: when `apps/web` uses it, add the package to `transpilePackages` and the files to `outputFileTracingIncludes` in `next.config.ts`.
- **Candidate accounts**: passwordless (magic link + Google, ADR-0008) in `apps/web/src/auth` (Better Auth, ADR-0011). Sign in at `/connexion`; in development the magic link is printed in the `npm run dev` log. The extension shares the web app's session through its host permission on `WXT_WEB_ORIGIN`; list the extension's `chrome-extension://<id>` origin in `EXTENSION_ORIGINS`.
- **Company Dossier**: `apps/web/src/company-dossiers` builds the dossier of an Application's employer from public data only. French employers are matched to a SIREN and read from the INSEE SIRENE register (`french-register.ts`, executives by role only); foreign ones come from `searchCompany` and are labelled less reliable, each fact kept only if it has the expected shape. A sole trader or unlisted SIREN is refused (`not_a_company`) before any search. A Presumed Employer is looked up only after the Candidate confirms it. Shown on `/candidatures/[id]`; API: `/api/applications/[id]/company-dossier` and `.../company-dossier/employer`.
- **Profiles from a CV**: `/profils/nouveau` uploads a PDF or Word (.docx) CV. `draftFromCv` (`apps/web/src/cv`) reads it into a draft Master CV and Search Criteria (AI task `cv_parsing`, with a rule-based fallback when the AI fails or its configuration is invalid; a Guest never needs AI configuration); the Candidate reviews it, and `createProfiles` (`apps/web/src/profiles`) saves it as a Profile with version 1 of its Master CV. No LinkedIn import (ADR-0001).
- **Master CV editor**: `/profils/[id]/cv` edits a Master CV, `/profils/[id]/versions` lists its versions and restores one. `saveMasterCv`, `masterCvVersions` and `restoreMasterCv` (`apps/web/src/profiles`) are scoped to the Candidate; a save based on an outdated version is refused (ADR-0012). API: `PUT /api/profiles/[id]/master-cv` and `POST /api/profiles/[id]/master-cv/restore`.
- **Several Profiles**: a Candidate creates a Profile from a CV or from scratch (`/profils/nouveau`), duplicates, renames, archives or restores it from its page (`PATCH /api/profiles/:id`, `POST /api/profiles/:id/duplicate`), and moves between active Profiles with the Profile switcher in the workspace header. The number of active Profiles respects the Plan Quota: the app passes billing's `profiles` limit to `createProfiles(database, { profileQuota })` (`profilePlanQuota`, `apps/web/src/profiles/plan-quota.ts`). A refused create, duplicate or restore answers 409 `{ error: "plan_quota_reached", prompt }`, where `prompt` is the Upgrade Prompt from billing's `allowsAnother`; the review form, the Profile page and `/profils/nouveau` show it.
- **Keeping a Guest's work**: the extension's analysis page sends a Guest to `/connexion` (sign in or create an account, no credentials stored in the extension) and rechecks the web session when the page comes back into view (`src/analysis-page.ts`, set up before the first render so a render that hangs cannot block it). `apps/extension/src/application-saving.ts` then turns the CV into a Profile (first one: Master CV version 1) or lets a Candidate pick a Profile, saves the Job Offer as an Application "À postuler", and clears the Guest session (ADR-0003, ADR-0011). It uses `GET /api/profiles`, `POST /api/profiles` and the Application route; a Web Lock makes tabs save one at a time. `fitProfileName` lives in `@jobhub/shared`.
- **Job Offers and Match Score**: `POST /api/job-offers` captures a Job Offer without an account (`apps/web/src/job-offers`); `POST /api/match-score` scores it (`apps/web/src/match-score`), against a Profile (`profileId`, signed in) or a CV sent in the request (Guest or Tailored CV, scored and never stored, ADR-0003). Each Match Score a signed-in Candidate requests counts against their Plan Quota (`matchScoreQuota`, wired to billing's `use(candidateId, "matchScores")` in `match-score/server.ts`, asked only once the Job Offer and CV are found); past it the route answers 402 with the Upgrade Prompt, which the extension's analysis page shows. A Guest's Match Scores are not counted, and an Application's Match Score, recomputed when it is shown, is not either. `POST /api/cv/draft` also reads a Guest's CV, by rules only (no AI, nothing saved). The extension (`apps/extension`) detects offers on the sites listed in `JOB_SITES` (`src/job-page.ts`), captures any other page by hand (`activeTab`), and keeps the Guest session (CV, offer, Kept Match Score: scored once per offer and Profile or CV (a signed-in Candidate scores against a Profile, by default the last chosen one, `chooseScoreAgainst`), given up as "unreachable" after `SCORE_TIMEOUT_MS` (90 s), `src/match-scoring.ts`) in session storage for at most `GUEST_RETENTION_HOURS` (ADR-0003); the worker job `guests.forget` runs every 15 minutes and deletes Guest-only Job Offers (`apps/web/src/job-offers/guest-retention.ts`, imported by the worker by relative path and copied in its Dockerfile). The scoring rules live in `scoreMatch` (`packages/shared/src/match-score`) so the extension and the web app score the same way (ADR-0013). A Job Offer skill counts as covered when one CV field (headline, summary, a skill, a job, a degree) holds its words in order, ignoring case, accents, plurals and small words, or any wording of the same line of the static FR/EN `SYNONYMS` table ("gestion de projet" / "project management", "S&OP" / "PIC"); skills are never read across two CV fields.
- **Onboarding without a CV**: `/profils/nouveau` offers both paths. The Onboarding Questionnaire (`apps/web/src/questionnaire`, pure: `startQuestionnaire` / `currentQuestion` / `answer` / `draftFromQuestionnaire`) asks one question at a time and gives the same `CvDraft` as `draftFromCv`, so both paths share the review form and `createProfiles`. Question wording lives in the catalogue (`questionnaire.questions.<id>`).
- **Coach Panel**: on every page a signed-in Candidate sees (root layout). A page declares what it shows with `<CoachInView kind="profile" id name />`; `createCoach` (`apps/web/src/coach`, AI task `coaching`) reads that Profile, scoped to the Candidate, into the AI Coach's context. `POST /api/coach` takes `{ conversationId?, message, focus? }` and returns `{ conversation, reply }`: Coach Conversations are saved server-side (`apps/web/src/coach-conversations`, two new tables created by `db:migrate`), an exchange only after the AI Coach replies. `GET`/`PATCH`/`DELETE` on `/api/coach/conversations[/id]` list, open, rename and delete them, for the signed-in Candidate only. The browser keeps only the open conversation's id. The worker job `coach-conversations.purge` runs nightly at 03:30 and deletes those whose last message is 12 months old or more.
- **Action Cards**: `createActionCards(database, { onAccept })` (`apps/web/src/action-cards`) — `propose` a card about a Profile or Application, list `pending` cards for a page, `decide` once (accept runs the kind's handler in the same transaction). Shown on the Profile page by `ActionCardList`; `POST /api/action-cards/:id` `{ decision }`. Each new kind (ATS Fix, Follow-up…) registers its handler in `apps/web/src/action-cards/server.ts`.
- **Tailored CV** (`apps/web/src/tailored-cv`): on `/candidatures/[id]` the AI Coach (AI task `writing`) proposes a Tailored CV in the Document Language (shared with the drafts, `tailored-documents/document-language.ts`). The proposal is rebuilt from the Master CV (ADR-0006): contact details copied, jobs/diplomas/languages/skills kept only if the Master CV has them, and a rephrased text stating a figure or a Job Offer keyword the Master CV lacks is replaced by the Master CV's. Requirements the Master CV lacks become questions; a confirmed one is added to the skills. The Candidate reviews the changes against the Master CV (`changes.ts`) with both Match Scores, then saves it on the Application; a proposal from an outdated Master CV Version cannot be saved (409). A refused AI reply (`reply.ts`: no JSON, bad JSON, wrong shape, no CV) is retried once, then the proposal is `unavailable`; each refusal logs a `console.warn` with its reason, attempt, reply length, provider and model, never the reply, CV or offer text. API: `GET`, `POST` (propose) and `PATCH` (answer) `/api/applications/[id]/tailored-cv`, `POST .../tailored-cv/save`.
- **Cover Letter and Outreach Message** (`apps/web/src/tailored-documents`): on `/candidatures/[id]` the AI Coach (AI task `writing`) drafts a Cover Letter and an Outreach Message (channel `email` or `inmail`), stored on the Application. The Document Language defaults to the Job Offer's (`jobOfferLanguage`, `packages/shared/src/document-language`). With a Company Dossier built, the Outreach Message names its Suggested Contact Roles. The Candidate edits a draft, drafts again (replaces it), copies it or opens it in their mail client (`mail-link.ts`, `mailto:`). Nothing is sent (ADR-0005). API: `GET`, `POST` (draft) and `PATCH` (edit) `/api/applications/[id]/tailored-documents`.
- **Application export**: `apps/web/src/application-exports` (`file(candidateId, applicationId, "tailored_cv" | "cover_letter", { format, template })`, null for another Candidate's Application or when nothing is saved) renders the saved Tailored CV or stored Cover Letter in its Document Language with the `@/export` renderers; file names add the employer after the Candidate's name (`ExportOptions.employer`). Cover Letters are signed with the Master CV's contact details. Shown as a "Download" group on `/candidatures/[id]`; API: `GET /api/applications/[id]/tailored-cv/export` and `.../cover-letter/export` (`format`, `template`).
- **Data export and account deletion (ADR-0010)**: the "Mes données" section of `/compte` downloads all of a Candidate's data as JSON (`GET /api/account/export`, `apps/web/src/candidate-data`) and deletes the account (`DELETE /api/account`, body `{ email }`, refused with 400 if it is not the Candidate's own). Billing's `closeAccount` deletes the Stripe customer first; the rest goes with the `candidate` row through `ON DELETE CASCADE`, except Job Offers and Plan Quotas. Every migration runs from `migrateDatabase` (`apps/web/src/migrations.ts`, also behind `npm run db:migrate`); add a new migration there, and `deletion-reach.test.ts` fails if a table tied to a Candidate is not deleted with them.
- **Follow-ups (ADR-0005)**: `createFollowUps` (`apps/web/src/follow-ups`; `proposeDue`, `onAccept`, `delays` / `setDelays`, `notices`) proposes a Follow-up Action Card once an Application has waited its Follow-up Delay in French working days, then an Abandonnée suggestion after two Follow-ups sent. The AI Coach drafts in the Document Language, with a plain template as fallback. The worker job `follow-ups.propose` runs every weekday at 06:00 UTC (built with `followUpsFromEnv`, mailer from `mailerFromEnv`) and emails only the Candidate. Accepting the card marks the Follow-up sent and moves the Application to "Relancée". Delays are edited on `/compte` (`PUT /api/follow-up-delays`, stored in `follow_up_delay`; created by `db:migrate`). `/candidatures` shows the « Relances à faire » notice.
 - **Plans and Plan Quotas (ADR-0014)**: `apps/web/src/billing` (`createBilling` → `entitlements`, `use`, `allowsAnother`, Stripe checkout / portal / webhooks, `setPlanQuotas`). Before doing metered work, call `use(candidateId, "matchScores" | "atsScores" | "enrichedContacts" | "jobSearches")` (or `allowsAnother(candidateId, "profiles", held)`); on a refusal, answer with `quotaExceededResponse` (API, 402) or render `<UpgradePrompt>` (pages). `planPrices()` gives the Plan Prices shown on `/abonnement` (read from the Stripe Prices, cached ~10 min; gives up after 2.5 s without retrying and, after a failure, is not asked again for a minute; `null` and no price row when Stripe is not configured or cannot give them; never hardcode a price). Plans come from Stripe webhooks; quotas are edited by Administrators (`ADMIN_EMAILS`) at `/admin/quotas`. Tests and e2e use the fake Stripe API in `apps/web/src/billing/fake-stripe.ts`. While a subscription is `past_due`, `entitlements().stripeStatus` makes `paymentFailedNotice` (`billing/payment-failed-notice.ts`) return the Payment Failed Notice: `<PaymentFailedBanner>` in the root layout shows it on every page except `/abonnement`, which shows it next to the current Plan, with a button POSTing to `/api/billing/portal`. To set up Stripe (test mode) and the Administrators for local development, run `scripts/setup/issue-22.sh`.
- **Human Coaches (ADR-0016)**: `apps/web/src/human-coaches` (`createHumanCoaches` → coaches, `coachSignedIn`, Coach Access, read-only `candidates` / `candidateFile` / `application`, `review` / `reviews`, `recordPaidSession` / `sessions`). Administrators add and retire coaches at `/admin/coachs` (booking link: https Cal.com only); Candidates pay and grant Coach Access at `/coachs`; coaches work in `/espace-coach` (404 for anyone else). Billing adds `coachingSessionPrice` and `startCoachingSessionCheckout`; the signed webhook records paid sessions. Needs `STRIPE_PRICE_COACHING_SESSION` and `..._PREMIUM` (both or neither, see `.env.example`). Tables are created by `db:migrate`. To set up the Coaching Session Prices, the webhook events and the first coaches, run `scripts/setup/issue-24.sh`.
- **Enriched Contacts (ADR-0015)**: `apps/web/src/enriched-contacts` (`createEnrichedContacts` → `get`, `find`, `reveal`, `contact`). One interface (`providers/types.ts`: `findPeople`, `getContactDetails`) with Lusha, Apollo and Kaspr adapters, tested on recorded answers through an injected fetch. Off unless `CONTACT_ENRICHMENT_PROVIDER`, its API key and `CONTACT_ENRICHMENT_DPA_SIGNED=true` are set (see `.env.example`). Finding is free; a reveal calls `billing.use(…, "enrichedContacts")` and gives the use back on failure. Routes: `/api/applications/[id]/enriched-contacts`. The Lusha adapter follows Lusha's v3 API (`docs/research/issue-77.md`): phones flagged do-not-call are left out of a reveal, and `waterfallEnabled` is not sent, so the account default applies. Kaspr's API shape is unconfirmed (see `docs/research/issue-23.md`) and Kaspr cannot search. The e2e suite uses the fake Apollo in `e2e/support/fake-contact-provider.mjs`. To pick the provider, record the signed DPA and set its API key, run `scripts/setup/issue-23.sh`. To check the Lusha adapter against the live API (costs credits), run `scripts/setup/issue-77.sh`.
- **Editing Search Criteria**: `changeSearchCriteria` (`apps/web/src/profiles`, `PATCH /api/profiles/[id]` with `{ searchCriteria }`) updates an active Profile's criteria; archived Profiles answer 409 `archived`. The inputs are shared with onboarding in `components/SearchCriteriaFields.tsx`. The Match Score ignores the target role (location, salary, contract type only).
- **Job Digests**: `createJobDigests` (`apps/web/src/job-digests`; `settings`, `subscribe` / `unsubscribe`, `unsubscribeByToken`, `claimDue`, `deliver`). The Candidate opts in per Profile at `/profils/[id]` (`POST` / `DELETE /api/profiles/[id]/job-digest`), daily or weekly within the `jobDigest` Plan Quota; above it the route answers with the Upgrade Prompt. The worker jobs `job-digest.schedule` (07:00 Europe/Paris, Mondays for weekly) and `job-digest.run` pick the Job Offers already stored with a Match Score at or above `JOB_DIGEST_MIN_MATCH_SCORE`, run `job-discovery` only to top up, and email the Candidate (mailer from `mailerFromEnv`, so the worker needs `APP_URL`, `SMTP_URL`, `MAIL_FROM`). A Job Offer the Profile was already shown is never listed again; a digest uses no Match Score or Job Search quota. Each email carries a `List-Unsubscribe` one-click link to `/desabonnement` (`POST /api/job-digests/unsubscribe`, token-based, no session); the digest is read at `/job-digests/[id]`. Tables are created by `db:migrate`.
- **Job discovery (ADR-0002)**: `createJobDiscovery({ ai, jobOffers }).discover(...)` (`apps/worker/src/job-discovery`) searches via `searchWeb`, fetches pages politely (`JobbboxBot`, robots.txt, no CAPTCHA/login/challenge bypass, no private addresses, Forbidden sites refused) and stores Job Offers through `apps/web/src/job-offers`. It reports found offers and skipped pages with reasons. The worker job `job-discovery.run` (`{ candidateId, profileId }`) uses the Profile's current Search Criteria; nothing schedules it yet. Web search calls Perplexity's Agent API (`POST /v1/responses`, `preset: "fast"`, `packages/ai/src/providers/perplexity.ts`); `AI_WEB_SEARCH_MODEL` overrides the preset's model and must be `provider/model`. A Job Search (`apps/web/src/job-searches`) uses one `jobSearches` Plan Quota unit; `createJobSearchReports(database, { quotas })` gives it back once when the search moves from searching to failed (including `queue_unavailable` and `timeout`), and the worker job `job-searches.expire` (every 5 minutes) fails searches left searching past `SEARCH_TIMEOUT_MS`. A run reads the provider URLs (sources first, then URLs named in the answer) in order, following up to 5 same-site postings from each Listing page (`listing-page.ts`, one level, `rel=nofollow` and robots `nofollow` honoured), until its Job discovery budget runs out (`jobDiscoveryBudgetFromEnv`, `apps/worker/src/job-discovery/budget.ts`): `JOB_DISCOVERY_BUDGET_JOB_OFFERS` (30), `JOB_DISCOVERY_BUDGET_EUR` (0.08), `JOB_DISCOVERY_BUDGET_SECONDS` (90, at most 600); an invalid value stops the worker at startup. A Greenhouse (`boards.greenhouse.io` / `job-boards.greenhouse.io/{board}/jobs/{id}`), Lever (`jobs.lever.co` / `jobs.eu.lever.co/{site}/{id}`) or Ashby (`jobs.ashbyhq.com/{board}/{id}`) posting is read through that ATS's public JSON API instead of its page (`ats.ts`, through the same polite fetcher): the Job Offer gets `postedAt` (`job_offer.posted_at`, from `first_published` / `createdAt` / `publishedAt`), and a closed posting (404, absent from the Ashby board, or past Greenhouse's `application_deadline`) is skipped as `gone`, one first published more than `MAX_POSTING_AGE_DAYS` (30) days ago as `too_old`. Only the posting's own API URL is requested (for Ashby, its employer's board, the only documented endpoint, downloaded once per run); ATS boards are never listed across employers. When the API cannot be read (larger than the fetcher's 3 MB limit, as OpenAI's 13 MB Ashby board, down, not JSON, or kept out by the API host's robots.txt), the posting's page is read instead under its own site's rules, without `postedAt`; an API answering with an anti-bot check is skipped as `bot_protection` and its page is not read either. `postedAt` is taken only from the caller's `trusted` argument to `capture` (a `Date`), never from a request body, so `POST /api/job-offers` cannot set it. Each run also records Discovery metrics (`packages/shared/src/discovery-metrics.ts`): a Job Search stores them in `job_search.metrics` (jsonb, added by `db:migrate`; null while searching and on older rows, not shown in the UI yet), and each Job Digest run logs one `job_digest_run` JSON line. Costs come from `costInEur` (`packages/ai/src/cost.ts`), estimated from list prices at `EUR_PER_USD = 0.86`; the Anthropic and OpenAI rates are unchecked. The worker's profiles dependency needs `masterCv.content` to count matches. `PERPLEXITY_LIVE=1` with a key runs the opt-in contract test `perplexity.live.test.ts`. To set up the Perplexity and offer-analysis keys for local development, run `scripts/setup/issue-13.sh`.
- **Expired Job Offers**: `createSourceRecheck({ store, fetch, forbiddenSites }).run(now)` (`apps/worker/src/source-recheck`) re-reads a Job Offer's source page through the same polite fetcher (ADR-0002) and returns `published`, `expired` (404/410 via the `gone` refusal, a past JSON-LD `validThrough`, a redirect to the site's home page, or, with no readable JobPosting, an expiry notice in the page body) or `unknown` (refusals and unreachable pages change nothing). `createSourceChecks(db)` (`apps/web/src/job-offers/source-checks.ts`) picks the due offers (`source_url` set, not Guest-only, unchecked for `RECHECK_INTERVAL_DAYS` = 3, or `EXPIRED_RECHECK_INTERVAL_DAYS` = 14 once expired) and records `source_checked_at` / `expired_at`; capturing the same source URL again clears `expired_at`. The worker job `job-offers.recheck-sources` runs daily at 04:00 UTC. `/candidatures`, `/candidatures/[id]` and `/offres/[id]` flag an Expired Job Offer; the Application Status is never changed.
- **Hosting**: EU only, see [`docs/ops/hosting.md`](docs/ops/hosting.md).
