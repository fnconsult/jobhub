# Jobbbox (jobhub)

Coaching platform for job seekers aged 40+ in France. Vocabulary: [`CONTEXT.md`](CONTEXT.md). Decisions: [`docs/adr/`](docs/adr/).

## Layout

| Workspace | What it is |
| --- | --- |
| `apps/web` | Next.js web app |
| `apps/extension` | Chrome MV3 extension (WXT) |
| `apps/worker` | Background-job runner (pg-boss on Postgres) |
| `packages/shared` | Domain types, translations (`@jobhub/shared/i18n`) and design tokens (`@jobhub/shared/design`) |
| `packages/ai` | Provider-agnostic AI layer (`@jobhub/ai`, server-side only): Anthropic, Mistral, OpenAI; web search (Search providers, ADR-0043): Perplexity's Search API, Brave, Tavily, with an optional fallback for the rest of a run; fake provider in `@jobhub/ai/testing` (`pending` waits for the request's `signal`); every result carries call facts, and a request's `signal` stops the call (Failure Reason `stopped`) |
| `packages/coach-knowledge` | The coaching knowledge files the one-off import reads (`@jobhub/coach-knowledge`, server-side only): `readCoachKnowledgeFiles()`, and the `[Sn]` / Sources table Markdown helpers |
| `packages/help` | The Help Articles (`@jobhub/help`, no AI call, browser and server): `articles/{fr,en}/<id>.md` (page, glossary and FAQ, with `kind`, `title`, `synonyms` and, for a page, `route`) bundled into `src/articles.generated.ts` by `npm run build -w @jobhub/help` (run it after editing an article; a test fails when it is stale). `articles`, `article`, `articleFor(route)` and `search(query, locale)`; `readHelpContent()` (Node only) checks the files. `apps/web/src/help/candidate-pages.test.ts` fails when a Candidate page has no page article |

## Getting started

Requires Node 22+ and Docker.

```sh
npm install
cp .env.example .env          # repo-root .env, read by `npm run dev`, `build`, `start` and `db:migrate`
docker compose up -d          # Postgres (host port 5433) + worker
npm run db:migrate            # create / upgrade the database tables
npm run dev                   # web app on http://localhost:3000
npm run dev -w @jobhub/extension   # extension, with a Chrome dev profile; its dev server is on http://localhost:3100
```

The `worker` container reads the same repo-root `.env` (AI layer keys and providers, `APP_URL`, …), so Job Searches and job discovery work locally. Its `DATABASE_URL` is overridden to `postgres:5432` inside the compose network. The `.env` is optional: without it the stack still starts, and job discovery runs without the sources whose keys are missing (France Travail, Fantastic.jobs, the web search), each named in the worker log. After editing `.env`, run `docker compose up -d` again to recreate the worker with the new values.

## Agent Run log

Delivery workflows (e.g. `wf-dev`) can record each Agent Run in the `workflow_agent_run` table (after `npm run db:migrate`):

```sh
npm run wf:record -- --issue 31 --workflow-id wf-dev --workflow-ref .claude/workflows/wf-dev.js \
  --workflow-instance wf_c2d1ad6a-1bc --workflow-date 2026-10-06T08:00:00Z \
  --agent "wf-dev/#31/implement" --model claude-opus-5-5 --effort high \
  --time-ms 754000 --round 0 --tokens 182345
```

`--round` defaults to 0 (first pass). `--workflow-date` is an ISO 8601 date (`2026-10-06`, read as UTC midnight) or a date-time with an explicit offset (`Z` or `+02:00`). Exits with code 2 and the usage line when a flag is missing or invalid.

## Conventions

- **Translations**: every user-facing string lives in `packages/shared/src/i18n/locales/*.json`. French (`fr`) is the default and reference locale; every locale must have the same keys.
- **Accessibility (ADR-0009)**: colours and type come from `packages/shared/src/design/tokens.ts`. `auditDesignTokens` checks WCAG 2.1 AA contrast, the 16px body-text floor and every text-size setting in the test suite. Light greys are for surfaces and borders only. `auditStylesheet` applies the same floor to a stylesheet (no text under 16px, only audited text colours, no literal colours outside custom properties). `apps/web/src/app/app-css.test.ts` runs it on `app.css`. `e2e/job-search.spec.ts` checks the Job Search results page at 1440, 900 and 375px; `JOB_SEARCH_SCREENSHOTS_DIR=<dir>` also saves its screenshots there (`docs/screenshots/job-search-results/`). The clickable layout prototype for #132 is `docs/prototypes/notion-layout.html` (one file, no dependencies, single light theme, no `<!doctype>` because the artifact host adds it); `docs/prototypes/notion-layout.test.ts` keeps its tokens equal to `renderDesignCss(designTokens)` and runs the stylesheet audit. Its layout decisions are proposals until François approves them.
- **Sidebar layout**: every Candidate page renders inside `components/CandidateLayout.tsx` (server; wraps `SidebarLayout.tsx`, client). Links come from `sidebarNav` (`components/sidebar-nav.ts`, route helpers in `routes.ts`); Job Searches and Job Digests have no index page, so they open the matching section of the Profile in view (or the first active Profile), and are left out without one. The hidden-sidebar choice is kept per browser on `<html data-sidebar>` (`design/sidebar-state.ts`, applied before first paint like the Text Size). Below 64rem the sidebar is a drawer. New Candidate pages must use `CandidateLayout`.
- **Complex widgets (ADR-0018)**: dialogs, menus, popovers and tabs use one unstyled `@radix-ui/react-<widget>` package each (never the whole `radix-ui` bundle), styled in `apps/web/src/app/app.css` with our tokens through classes and `data-*` attributes. The Profile switcher (`components/ProfileSwitcherMenu.tsx`) is the first; the sidebar drawer (`components/SidebarLayout.tsx`, a Dialog) is the second. No Tailwind or shadcn.
- **AI calls (ADR-0007)**: always through `@jobhub/ai` (`createAiLayerFromEnv()` → `generate` / `searchWeb` / `searchCompany`), never a provider SDK directly. The provider of each task is set by `AI_<TASK>_PROVIDER` / `AI_<TASK>_MODEL` (see `.env.example`). Tasks that carry personal data refuse non-EU endpoints at start-up and on every call; web search (`AI_WEB_SEARCH_PROVIDER`: perplexity, brave or tavily, and `AI_WEB_SEARCH_FALLBACK_PROVIDER`; one filter contract of domains, country, page age and result count, each handled by the provider or emulated on the pages it returns) only ever receives a query built from Search Criteria (the title alone also goes to the `job_titles` task, `AI_JOB_TITLES_PROVIDER` / `AI_JOB_TITLES_MODEL`, default the offer analysis ones, to get Job title variants), or from an employer's name for a Company Dossier (`searchCompany`; never a person's name, see the ADR-0007 amendment). With a Candidate's EU AI Consent (`eu_ai_consent`, set on `/compte`), a call that carries their identity (declare `containsIdentity: true`; undeclared phone numbers or emails are caught by a scan and logged) goes to Mistral (`AI_IDENTITY_MODEL`, needs `MISTRAL_API_KEY`), see the ADR-0007 amendment; pass `euAiConsent` to `createAiLayerFromEnv`. Every call logs its token usage per Candidate (`ai_usage` JSON lines). Tests use `createFakeProvider` from `@jobhub/ai/testing`, or `AI_FAKE=true`.
- **Coaching Playbooks (ADR-0019, ADR-0021, #225)**: the Coaching Playbooks, the Core Digest and the Sources list live in the database as Playbook Versions kept forever (`apps/web/src/coaching-playbooks`), written in the Back Office (`/admin/playbooks`) by the Playbook editor role (super-admins too; Support reads). `npm run db:migrate` imports `packages/coach-knowledge` once, as version 1 of each, none Human-validated, each playbook with a default Playbook Agent (the AI Coach's route, effort medium, when to consult it). A version not yet validated is edited in place; changing a validated one makes a new version; an Administrator other than its authors validates it, naming themselves. Production (`JOBHUB_TARGET=production`, or a production build naming no target) serves the latest Human-validated version of each; staging, e2e and development the latest one. Every `[Sn]` is checked against the Sources list on save, and a Source cited by a served version cannot be removed. Archived playbooks are kept, never served.
- **Playbook Agents (#225)**: for each reply the AI Coach chooses at most two Playbook Agents from the served playbooks' "when to consult it" (`apps/web/src/coach/playbook-agents.ts`); each gets the Coach context and its playbook, on its own provider, model and effort (any text provider configured; every call is redacted) (`AiLayer.generate({ route, effort })`, `agentModels()`); the AI Coach then writes the reply with the Core Digest, the advice (marked as data) and the Sources cited, the whole prompt within the 12k cap. A Playbook Agent that fails or times out is left out, logged without content. The reply records the Core Digest and versions consulted (`coach_message.playbooks`) and each consultation's cost (`coach_message.consultations`); the coach cost page shows both, with the median cost per Playbook Agent.
- **Explainable labels (#407, ADR-0042)**: `components/ExplainableLabel.tsx` is a button (plain text outside the Back Office Assistant) that calls `useAskAssistant()` from `CoachPanel.tsx`, sending « Explique-moi « <label> » ici. » with the item's context (`explainedSchema` in `back-office-assistant/explained.ts`). The context is saved in `explained` (jsonb) on the Administrator's message, told again every turn inside `<donnees>`, and included in the Data export; a Provider Secret's value or a hidden env variable's is never told. Used on Paramètres rows (`SettingName.tsx`), Sources, missing-key warnings and Environnement; Dashboard figures and run stop reasons wait for those pages. E2e: `e2e/explainable-labels.spec.ts` (the « Pays » case skips until JOB_DISCOVERY_COUNTRY exists).
- **Guardrails (#228, ADR-0022)**: `apps/web/src/guardrails` fixes the five Guardrails in code (`prompt_injection`, `personal_data_leak`, `secret_disclosure`, `harmful_advice`, `distress`; the Back Office Assistant gets the first three). `guard(agent, request)` checks distress words, makes one AI check on the input (AI task `guardrail`, `AI_GUARDRAIL_PROVIDER` / `AI_GUARDRAIL_MODEL`, default the coaching ones; any configured provider, every call redacted, ADR-0007 amendment), has the reply written, applies the fixed rules (`identityIn` in `packages/ai/src/identity-scan.ts`, copied instructions, key shapes), then checks the output. A check that fails or times out lets the text through and records an `unavailable` Guardrail Trigger with a `reason` (`GUARDRAIL_FAILURE_REASONS`: `guardrail_timeout`, `invalid_verdict`, `provider_error`; null on older rows, shown as « Raison non enregistrée »; counted per reason by `triggersPerDay().unavailableBy`). Settings, versioned Guardrail messages (validated per language by someone other than the author; production serves validated ones, the French and English defaults apply until then) and Triggers (no Candidate or text; the worker job `GUARDRAIL_TRIGGERS_PURGE` deletes them after 24 months) are in `guardrail_setting`, `guardrail_message` and `guardrail_trigger`; super-admins tune them at `/admin/garde-fous` (Support reads), every change in the Journal. A blocked message is not given to the AI and is marked `blocked` (Coach Panel label, Data export); a replaced reply is saved only as its Guardrail message. The fake Mistral logs the system prompt for `E2E_SHOW_CONTEXT#<tag>` (`e2e/support/system-prompt.ts`) because echoing it is now blocked.
- **Candidate accounts**: passwordless (magic link + Google, ADR-0008) in `apps/web/src/auth` (Better Auth, ADR-0011). Sign in at `/connexion`; in development the magic link is printed in the `npm run dev` log. The extension shares the web app's session through its host permission on `WXT_WEB_ORIGIN`; list the extension's `chrome-extension://<id>` origin in `EXTENSION_ORIGINS`.
- **Company Dossier**: `apps/web/src/company-dossiers` builds the dossier of an Application's employer from public data only. French employers are matched to a SIREN and read from the INSEE SIRENE register (`french-register.ts`, executives by role only); foreign ones come from `searchCompany` and are labelled less reliable, each fact kept only if it has the expected shape. A sole trader or unlisted SIREN is refused (`not_a_company`) before any search. A Presumed Employer is looked up only after the Candidate confirms it. Shown on `/candidatures/[id]`; API: `/api/applications/[id]/company-dossier` and `.../company-dossier/employer`.
- **Profiles from a CV**: `/profils/nouveau` uploads a PDF or Word (.docx) CV. `draftFromCv` (`apps/web/src/cv`) reads it into a draft Master CV and Search Criteria (AI task `cv_parsing`, with a rule-based fallback when the AI fails or its configuration is invalid; a Guest never needs AI configuration); the Candidate reviews it, and `createProfiles` (`apps/web/src/profiles`) saves it as a Profile with version 1 of its Master CV. No LinkedIn import (ADR-0001).
- **Master CV editor**: `/profils/[id]/cv` edits a Master CV, `/profils/[id]/versions` lists its versions and restores one. `saveMasterCv`, `masterCvVersions` and `restoreMasterCv` (`apps/web/src/profiles`) are scoped to the Candidate; a save based on an outdated version is refused (ADR-0012). API: `PUT /api/profiles/[id]/master-cv` and `POST /api/profiles/[id]/master-cv/restore`.
- **Several Profiles**: a Candidate creates a Profile from a CV or from scratch (`/profils/nouveau`), duplicates, renames, archives or restores it from its page (`PATCH /api/profiles/:id`, `POST /api/profiles/:id/duplicate`), and moves between active Profiles with the Profile switcher in the sidebar. The number of active Profiles respects the Plan Quota: the app passes billing's `profiles` limit to `createProfiles(database, { profileQuota })` (`profilePlanQuota`, `apps/web/src/profiles/plan-quota.ts`). A refused create, duplicate or restore answers 409 `{ error: "plan_quota_reached", prompt }`, where `prompt` is the Upgrade Prompt from billing's `allowsAnother`; the review form, the Profile page and `/profils/nouveau` show it.
- **Place suggestions (#235)**: the Search Criteria location field (`LocationsInput`, chips; `places-input.ts` holds the duplicate and five-place rules) asks `GET /api/places?q=` (signed-in only, 401 otherwise), which queries geo.api.gouv.fr through `places/geo-api.ts` (communes, then départements, then régions, 8 at most; nothing under 3 characters; answers kept 10 minutes; a failure gives no suggestion). Calls are traced as tool `geo-api-gouv` (path only, never the query). Places stay plain strings; `locationKey` (`@jobhub/shared`) is the same-place test. No key needed. Read the API's usage terms (https://geo.api.gouv.fr/cgu) before production traffic.
- **Sectors, Subsectors and Domains (#236, ADR-0025)**: Search Criteria `sectors` (NAF rév. 2 sections), `subsectors` (divisions) and `domains` (France Travail ROME 4.0 professional domains) are lists of codes, empty meaning no preference. The accepted codes and which Sector each Subsector belongs to are fixed in `packages/shared/src/sectors.ts`; the labels are Reference data (`apps/web/src/reference-data`, table `reference_label`), read from INSEE's SPARQL endpoint and France Travail's ROME open data (no key needed), fetched on first read and refreshed by the worker job `reference-data.refresh` (monthly, the 2nd at 05:00); a failing source keeps its labels. Both are Tools (`insee-naf`, `rome-open-data`) and calls are traced. `GET /api/reference-data` (signed-in only) serves the labels to `IndustryInputs`. The France Travail `secteurActivite` and `domaine` filters are unverified against a live answer (`docs/research/issue-236.md`). E2e fakes both sources with `e2e/support/fake-reference-data.mjs`.
- **Keeping a Guest's work**: the extension's analysis page sends a Guest to `/connexion` (sign in or create an account, no credentials stored in the extension) and rechecks the web session when the page comes back into view (`src/analysis-page.ts`, set up before the first render so a render that hangs cannot block it). `apps/extension/src/application-saving.ts` then turns the CV into a Profile (first one: Master CV version 1) or lets a Candidate pick a Profile, saves the Job Offer as an Application "À postuler", and clears the Guest session (ADR-0003, ADR-0011). It uses `GET /api/profiles`, `POST /api/profiles` and the Application route; a Web Lock makes tabs save one at a time. `fitProfileName` lives in `@jobhub/shared`.
- **Job Offers and Match Score**: `POST /api/job-offers` captures a Job Offer without an account (`apps/web/src/job-offers`); `POST /api/match-score` scores it (`apps/web/src/match-score`), against a Profile (`profileId`, signed in) or a CV sent in the request (Guest or Tailored CV, scored and never stored, ADR-0003). Each Match Score a signed-in Candidate requests counts against their Plan Quota (`matchScoreQuota`, wired to billing's `use(candidateId, "matchScores")` in `match-score/server.ts`, asked only once the Job Offer and CV are found); past it the route answers 402 with the Upgrade Prompt, which the extension's analysis page shows. A Guest's Match Scores are not counted, and an Application's Match Score, recomputed when it is shown, is not either. `POST /api/cv/draft` also reads a Guest's CV, by rules only (no AI, nothing saved). The extension (`apps/extension`) detects offers on the sites listed in `JOB_SITES` (`src/job-page.ts`), captures any other page by hand (`activeTab`), and keeps the Guest session (CV, offer, Kept Match Score: scored once per offer and Profile or CV (a signed-in Candidate scores against a Profile, by default the last chosen one, `chooseScoreAgainst`), given up as "unreachable" after `SCORE_TIMEOUT_MS` (90 s), `src/match-scoring.ts`) in session storage for at most `GUEST_RETENTION_HOURS` (ADR-0003); the worker job `guests.forget` runs every 15 minutes and deletes Guest-only Job Offers (`apps/web/src/job-offers/guest-retention.ts`, imported by the worker by relative path and copied in its Dockerfile). On `/offres/[id]` a signed-in Candidate sees the score and its reasons (`MatchScoreWhy`, `ProfileMatchScore` in `components/`), chosen by `jobOfferMatch` (`match-score/job-offer-match.ts`): the Application's Profile once saved, else the active Profile named by `?profil=<profileId>` (added to Job Search, Job Digest and Job Digest email links) or the first one; like the Application's, it is recomputed when shown and not counted. The scoring rules live in `scoreMatch` (`packages/shared/src/match-score`) so the extension and the web app score the same way (ADR-0013). A Job Offer skill counts as covered when one CV field (headline, summary, a skill, a job, a degree) holds its words in order, ignoring case, accents, plurals and small words, or any wording of the same line of the static FR/EN `SYNONYMS` table ("gestion de projet" / "project management", "S&OP" / "PIC"); skills are never read across two CV fields.
- **Onboarding without a CV**: `/profils/nouveau` offers both paths. The Onboarding Questionnaire (`apps/web/src/questionnaire`, pure: `startQuestionnaire` / `currentQuestion` / `answer` / `draftFromQuestionnaire`) asks one question at a time and gives the same `CvDraft` as `draftFromCv`, so both paths share the review form and `createProfiles`. Question wording lives in the catalogue (`questionnaire.questions.<id>`).
- **Coach Panel**: on every page a signed-in Candidate sees (root layout); its button is in the top bar of the Candidate pages (floating elsewhere), and the panel is docked from 80rem. A page declares what it shows with `<CoachInView kind id name profileId? />` (`profile`, `application`, `job_offer`, `job_search` or `job_digest`); `createCoach` (`apps/web/src/coach`, AI task `coaching`) builds the context with `coachContext` (`coach/context.ts`), every read scoped to the Candidate: the Candidate summary (first name only; the Master CV identity is stripped, so the call is not identity-bearing, ADR-0007), the item In view in full, then summaries (onboarding answers, 5 latest Applications, top 5 Job Offers by Match Score), trimmed before the item In view to fit `COACH_CONTEXT_MAX_TOKENS` (12k estimated tokens, about 4 characters each). `POST /api/coach` focus is `{ kind, id, profileId? }`; a new Coach Conversation attaches to the Profile in view or `focus.profileId`. `POST /api/coach` takes `{ conversationId?, message, focus? }` and returns `{ conversation, reply }`: Coach Conversations are saved server-side (`apps/web/src/coach-conversations`, two new tables created by `db:migrate`), an exchange only after the AI Coach replies. `GET`/`PATCH`/`DELETE` on `/api/coach/conversations[/id]` list, open, rename and delete them, for the signed-in Candidate only. The browser keeps only the open conversation's id. The worker job `coach-conversations.purge` runs nightly at 03:30 and deletes those whose last message is 12 months old or more.
- **Action Cards**: `createActionCards(database, { onAccept })` (`apps/web/src/action-cards`) — `propose` a card about a Profile or Application, list `pending` cards for a page, `decide` once (accept runs the kind's handler in the same transaction). Shown on the Profile page by `ActionCardList`; `POST /api/action-cards/:id` `{ decision }`. Each new kind (ATS Fix, Follow-up…) registers its handler in `apps/web/src/action-cards/server.ts`.
- **Coach Memory (#125)**: `createCoachMemory` (`apps/web/src/coach-memory`; `propose`, `confirm`, `list`, `edit`, `delete`) keeps up to 30 key facts per Candidate (kind `goal`, `constraint` or `decision`, 300 characters each) in `coach_memory_item` (created by `db:migrate`, deleted with the account, included in the Data export). `propose` asks the AI Coach (task `coaching`) for the key facts of one of the Candidate's Coach Conversations and saves nothing; only `confirm` saves, once per fact (same words whatever the case and spacing). `createCoach` sends the Coach Memory with every message. API, for the signed-in Candidate only: `POST /api/coach/memory/proposals` `{ conversationId }`, `GET`/`POST /api/coach/memory`, `PATCH`/`DELETE /api/coach/memory/[id]`. In the Coach Panel: « Que retenir de cette conversation ? » under a conversation, « Mémoire du coach » to view, edit and delete.
- **Coach Message Cost (#127)**: `createCoach` returns `cost` (`CoachMessageCost`: provider, model, input, output and cached tokens, EUR estimate) with each `reply`, never sent to the browser; `coach-conversations` stores it on the AI Coach's `coach_message` row (columns added by `db:migrate`, null on Candidate messages and older replies). `coachCostPerDay(database, since)` gives per Paris-time day the replies, median and p90 EUR and token totals; `COACH_MESSAGE_COST_TARGET_EUR` is 0.03. Administrators see the last 30 days at `/admin/cout-coach`. `TokenUsage` has `cachedInputTokens` and `cacheWriteTokens` (`inputTokens` excludes cache reads); `costInEur` prices cache reads at 0.1x the input price (0.05x for Opus 5.5 and Sonnet 5.5) and Anthropic cache writes at 1.25x. Costs are estimates at `EUR_PER_USD`.
- **Tailored CV** (`apps/web/src/tailored-cv`): on `/candidatures/[id]` the AI Coach (AI task `writing`) proposes a Tailored CV in the Document Language (shared with the drafts, `tailored-documents/document-language.ts`). The proposal is rebuilt from the Master CV (ADR-0006): contact details copied, jobs/diplomas/languages/skills kept only if the Master CV has them, and a rephrased text stating a figure or a Job Offer keyword the Master CV lacks is replaced by the Master CV's. Requirements the Master CV lacks become questions; a confirmed one is added to the skills. The Candidate reviews the changes against the Master CV (`changes.ts`) with both Match Scores, accepting or rejecting each (a change flagged with Job Offer words starts undecided), then saves it on the Application: `save` takes `{ revision, accepted }` and stores `withChanges(...)`, so a rejected change keeps the Master CV's content and a flagged one is saved only if its id is sent; a proposal from an outdated Master CV Version cannot be saved (409). A refused AI reply (`reply.ts`: no JSON, bad JSON, wrong shape, no CV) is retried once, then the proposal is `unavailable`; each refusal logs a `console.warn` with its reason, attempt, reply length, provider and model, never the reply, CV or offer text. API: `GET`, `POST` (propose) and `PATCH` (answer) `/api/applications/[id]/tailored-cv`, `POST .../tailored-cv/save`.
- **Cover Letter and Outreach Message** (`apps/web/src/tailored-documents`): on `/candidatures/[id]` the AI Coach (AI task `writing`) drafts a Cover Letter and an Outreach Message (channel `email` or `inmail`), stored on the Application. The Document Language defaults to the Job Offer's (`jobOfferLanguage`, `packages/shared/src/document-language`). With a Company Dossier built, the Outreach Message names its Suggested Contact Roles. The Candidate edits a draft, drafts again (replaces it), copies it or opens it in their mail client (`mail-link.ts`, `mailto:`). Nothing is sent (ADR-0005). API: `GET`, `POST` (draft) and `PATCH` (edit) `/api/applications/[id]/tailored-documents`.
- **Application export**: `apps/web/src/application-exports` (`file(candidateId, applicationId, "tailored_cv" | "cover_letter", { format, template })`, null for another Candidate's Application or when nothing is saved) renders the saved Tailored CV or stored Cover Letter in its Document Language with the `@/export` renderers; file names add the employer after the Candidate's name (`ExportOptions.employer`). Cover Letters are dated the day of the export (`now` dependency, i18n `cvDocument.letterDate`) and show the Master CV's contact details once; the stored text goes through `coverLetterBody` (`tailored-documents/cover-letter-body.ts`), which keeps only the plain-text body (no Markdown, header, signature or `[…]` placeholders), when drafted and when exported. Shown as a "Download" group on `/candidatures/[id]`; API: `GET /api/applications/[id]/tailored-cv/export` and `.../cover-letter/export` (`format`, `template`).
- **Data export and account deletion (ADR-0010)**: the "Mes données" section of `/compte` downloads all of a Candidate's data as JSON, derived data included (GDPR art. 15; `GET /api/account/export`, `apps/web/src/candidate-data`, research in `docs/research/issue-171.md`), leaving out only secrets, Human Coaches' contact details and providers' ids or costs and deletes the account (`DELETE /api/account`, body `{ email }`, refused with 400 if it is not the Candidate's own). Billing's `closeAccount` deletes the Stripe customer first; the rest goes with the `candidate` row through `ON DELETE CASCADE`, except Job Offers and Plan Quotas. Every migration runs from `migrateDatabase` (`apps/web/src/migrations.ts`, also behind `npm run db:migrate`); add a new migration there, and `deletion-reach.test.ts` fails if a table tied to a Candidate is not deleted with them or is missing from `EXPORTED_TABLES` (`candidate-data`, where each table lands in the export).
- **Follow-ups (ADR-0005)**: `createFollowUps` (`apps/web/src/follow-ups`; `proposeDue`, `onAccept`, `delays` / `setDelays`, `notices`) proposes a Follow-up Action Card once an Application has waited its Follow-up Delay in French working days, then an Abandonnée suggestion after two Follow-ups sent. The AI Coach drafts in the Document Language, with a plain template as fallback. The worker job `follow-ups.propose` runs every weekday at 06:00 UTC (built with `followUpsFromEnv`, mailer from `mailerFromEnv`) and emails only the Candidate. The worker job `job-offers.recheck-sources` runs daily at 04:00 UTC. `/candidatures`, `/candidatures/[id]` and `/offres/[id]` flag an Expired Job Offer; the Application Status is never changed.
