# Candidate accounts on Better Auth, shared with the extension by cookie

Passwordless sign-in (ADR-0008) is built on Better Auth rather than Auth.js or hand-rolled code: it ships magic links and Google (Apple later) on our own Postgres, keeps everything in the EU database (ADR-0007), and has an organisation plugin that matches ADR-0004. Its account table is named `candidate`, so the code speaks the domain language; the Candidate's Interface Language is a column on it (default `fr`).

The browser extension holds no session or token of its own. Its host permission on the web app lets Chrome send the web app's session cookie with the extension's requests, so signing in or out on the web app signs the extension in or out too; the extension's `chrome-extension://<id>` origins are listed as trusted so it may also act for the Candidate. We rejected bearer tokens stored in the extension: a second credential to issue, store and revoke, for no gain while the extension only works alongside the web app.

Organisations (ADR-0004) will be added with the organisation plugin: it only creates `organization`, `member` and `invitation` tables referencing `candidate`, and adds a nullable column to `session`. Candidate data is never migrated; a test checks the plan stays additive.

## Addendum (#209): Sign-in Providers configured at runtime from the database

Sign-in providers beyond the magic link are no longer environment variables: super-admins configure them in the Back Office (the Connexion section), and they are kept in a `sign_in_provider` table, their secrets as Provider Secrets (ADR-0020). Google, Apple and Microsoft go through Better Auth's `socialProviders`, any generic OIDC provider through its `genericOAuth` plugin; we do not use the `sso` plugin, and there is no SAML. Better Auth reads its providers once, when an instance is built, so the web app builds a new instance whenever the configuration changes (announced by Postgres NOTIFY, like the Provider Secrets); the new instance shares the tables and `AUTH_SECRET`, so nobody is signed out. Who may use which provider (shown to Candidates, allowed for Administrators), which providers link accounts by email (`accountLinking.trustedProviders`, read from the database) and how each session was signed in are decided in our database hooks on every OAuth callback. An untrusted provider never takes over an existing account by email: the person signs in by magic link and links it from Mon compte. Apple's client secret is a JWT we sign from the `.p8` key, again every month by the worker. Env's `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are seeded once as a database provider, and stay the fallback for its secret and for a process that cannot read the table.

We rejected Better Auth's `sso` plugin: it targets per-organisation enterprise SSO (domain routing, SAML), which ADR-0004 does not need yet, and it would have kept Google on a separate path.
